## 一、先看结论

**区块链部分已形成可运行、可测试的本地研究原型，但尚未成为公开发行、真实资金结算或生产贡献认证系统。** 当前最完整的新模块是 Flower：可信发行者审核合成贡献，接收者签名同意，在临时本地链铸造永久不可转让 NFT，再查询或撤销认可状态。

必须把四件事分开理解：

1. **PayAssist 是当前攻防评估主线。** 它研究模型提案、宿主拦截、模拟落账、修复与回归，不依赖公开发行代币。
2. **XEXP 支付实验是独立 EVM 研究链路。** `ExperimentalToken`、`PaymentAgent`、`RewardSettlement` 展示合成资产的付款执行及独立奖励；不是公众支付业务。
3. **RTM 是保留的历史 ERC-20 悬赏研究。** `RTMToken` 与 `BountyVault` 没有被改名为 NFT，也没有与 Flower 兑换或合并；旧 Arena 有本地奖励桥，当前 PayAssist campaign 未接入。
4. **Flower 是另一份 ERC-721 / ERC-5192 合约。** 它表达贡献认可，不是金融奖励，没有销售、兑换、提现、收益、算力或商业服务资格权益。

**本地链发生过真实 EVM 状态更新，不等于公网链已经部署；静态 NFT 快照可展示，不等于公众已经领取。** 当前没有证据支持宣称项目已开放认证式公众投稿、公开发放 NFT、运营真实资金悬赏，或取得生产安全/合法性认证。

### 1.1 产品关系图

```text
REDTEAM
├─ 当前研究主线：PayAssist L0/L1
│  └─ 授权任务 → 攻击/对照 → 分层判定 → 修复 → 回归门禁
│     └─ 尚未自动连接 RTM 奖励或 Flower 发放
├─ 独立本地 EVM 支付实验
│  ├─ ExperimentalToken（XEXP）→ 预充 PaymentAgent → 实验付款
│  └─ XEXP 独立预充 RewardSettlement → evaluator 审定的演示奖励

│  ├─ 旧 Arena 证据/claim 登记 → RTM bridge → BountyVault → 铸造 RTM
│  └─ BountyRound：材料哈希先到先得 → owner 裁决 → 本地原生币 pull 领奖

└─ 独立贡献认可旁路：REDTEAM Flower
```

## 四、支付与金融奖励研究：具体实现了什么

### 4.1 XEXP 支付实验：执行约束与商业判定分离

[ExperimentalToken.sol](../../contracts/src/ExperimentalToken.sol) 是 `Experimental Token / XEXP`，全部供应量在构造时铸给部署者，要求供应量大于零，之后没有 mint 接口。演示把资产分别预充到付款合约和奖励合约，不使用 RTM 或 Flower。

[PaymentAgent.sol](../../contracts/src/PaymentAgent.sol) 的关键接口是：

- `setAllowlisted(address a, bool ok)`：只有不可变 `operator` 可调整白名单。
- `configureInvoice(bytes32 id, address merchant, address participant, uint256 amount)`：一次性登记发票；双方须在白名单内，金额须在额度内。
- `pay(bytes32 op, bytes32 invoice, address merchant, address participant, uint256 amount)`：精确匹配发票，重新检查白名单，分别消耗 `usedOps` 与 `usedInvoices`，要求 `totalPaid + amount <= maxPayment`，再经 `SafeERC20.safeTransfer` 转给 participant。

两个 ID 采用分离映射，避免一个操作 ID 无意消耗同值发票 ID。`maxPayment` 同时限制单笔配置金额和累计付款，不等于运行时每笔提案上限；两层限制应分别读取场景与合约配置。

**机械匹配不是授权真实性证明。** 同一个 operator 能登记发票和执行付款；如果可信宿主错误接受外部话术并把错误条款登记进去，合约不会理解“货没交付”或“用户其实没授权”。operator 固定为部署者、不能轮换，密钥泄漏后的处置能力也不能按生产治理表述。源码中使用的是 `PaymentAgent` 和 OpenZeppelin `SafeERC20`，不是另一个名为 `SafePayment` 的已实现合约。

[RewardSettlement.sol](../../contracts/src/RewardSettlement.sol) 则由不可变 `evaluator` 调用 `configureSettlement` 与 `settle`，校验受益人/金额、禁止重复结算并限制累计 `paid`。演示由不同账户分别部署付款与奖励合约，使余额、权限与额度独立；这是 **XEXP 实验奖励**，不是 RTM 铸币或 Flower 认可。

### 4.2 本地流程与证据

[agent-flow.js](../../contracts/scripts/agent-flow.js) 调用 Python 决策运行时，使用确定性 mock；传入子进程前移除相关模型网络配置，并检查返回 backend 为 mock。`vulnerable` / `hardened` 是研究对照模式，前者刻意保留错误信任路径，后者按可信业务 feed 核验。

流程记录以下不同事实，不把它们合并为“安全成功”：

| 层次 | 记录或检查 | 解释 |
|---|---|---|
| 模型提案 | parsed proposal、attempted violations | 模型违规提案即使未执行也应保留 |
| 宿主/合约阻止 | `executor_blocked`、执行错误 | 被拦截不是已经付款 |
| 实际本地落账 | 交易/回执、Payment 与指定 token 的 Transfer、余额变化 | 不能用模型自述或任意同名事件替代 |
| 独立业务判定 | evaluator truth、`wrong` / `legitimate` | 可信付款 feed 与评价真值不混用 |
| 后续失败 | `evaluation_failed`、`reward_failed` | 判定或奖励失败不能抹去已经挖出的付款 |

[payment-evaluator.js](../../contracts/scripts/payment-evaluator.js) 校验回执成功、目标合约、指定地址的 Payment/Transfer 及金额和收款方一致，再按独立真值判断。付款损失与奖励出款分别记账，未完成判定的付款保持未知，不能默认为零损失。

局限是：局部 helper 接收的回执对象本身不是独立的公网共识证明；正常 runner 的回执来自本地 provider 的 `tx.wait()`。同样，`assertLocalChain` 是这条演示的本地检查，不应与 Flower 更严格的多层网络防护混称。

### 4.3 历史 RTM：供应上界与金库预算

[RTMToken.sol](../../contracts/src/RTMToken.sol) 是 `REDTEAM / RTM` 的 **ERC-20**，不是 NFT。当前机制包括：

- `MAX_SUPPLY = 21,000,000 RTM`，部署时零预铸；这个数字是供应上界，不是已经发行量。
- 年 0 预算为 10,500,000 RTM；`yearBudget(n) = YEAR0_BUDGET >> n`。每年按固定 365 天窗口，不是公历年度。
- `minter` 在部署时永久绑定已部署的合约；owner 不能直接 mint、改发行起点或更换 minter。
- mint 同时检查当年预算与剩余供应上界；整数减半排程总和比上界少 38 个最小单位。

[BountyVault.sol](../../contracts/src/BountyVault.sol) 并不托管现成 RTM 余额，而是在结算时作为唯一 minter 铸币。部署顺序为金库 → `RTMToken(minter=vault)` → 一次性 `initializeRtm` → owner 配置 evaluator/额度。

权限与状态如下：

| 权限/接口 | 实现含义 | 不能扩大为 |
|---|---|---|
| owner：`setEvaluator`、`setMaxPerClaim`、`setMaxTotalSettled` | 轮换评估者和调整额度 | 多签、独立多方治理或自动识别恶意评估者 |
| evaluator：`configureClaim` | 绑定受益人/金额/当前发行年，预留尚未铸出或占用的预算 | 贡献已被链上独立审核 |
| evaluator：`settleClaim` | 当前年内再次检查额度，更新终态后 mint；失败原子回滚 | 无条件兑付或真实购买力 |
| evaluator：`cancelClaim` / `renewClaim` | 取消释放预留；过期 claim 可保持受益人/金额重新预留当前年预算 | 跨年自动续期、预算不足时保证领奖 |
| owner：`pause` / `unpause` | 暂停/恢复 claim 操作 | 销毁既有记录或消除已经发生的发行 |
| `renounceOwnership` 禁用 | 避免失去管理者后无法初始化/解暂停 | owner 不会失误或不会滥用 |

`maxPerClaim` 初始为零，需要显式配置；`maxTotalSettled` 默认 `uint256.max`，即没有额外收紧。单笔上限不能自动防止评估者以多笔耗尽年度预算，累计上限必须由 owner 实际配置，暂停与轮换也仍依赖 owner。

### 4.4 旧 Arena 证据桥：已连接的边界

[证据奖励协议 v1](../EVIDENCE_REWARD_PROTOCOL.md)记录目标、任务授权、证据 manifest、验证协议、受益人和金额。Python 的 [claim_protocol.py](../../rsi4safety/execution/src/rsi4safety/claim_protocol.py) 与 JS 的 [claim-id.js](../../contracts/scripts/claim-id.js) 使用同一常量测试锚点。

RTM claim ID 为五个字符串字段的规范化 JSON 的 SHA-256：`protocol`、`dedup_key`、`sut_digest`、`beneficiary`、`amount`。**金额和受益人是 RTM claim ID 的一部分**；改变任一绑定字段会改变 ID。链上只保证同一个 ID 不再配置，内容/机制去重依赖可信链下登记，不是跨钱包、跨部署的普遍语义去重。

[rtm-reward-bridge.js](../../contracts/scripts/rtm-reward-bridge.js) 读取旧 Arena 的 `claim-requests.jsonl`，筛选 pending、按 claim ID 合并，再逐项 `configureClaim → settleClaim`，单项失败保留在返回结果中而不阻塞全部项目。

这不是任意公众上传文件即领取奖励的可信入口：

- 消费函数本身不重新裁决原始攻击，不重算登记 ID，也不完整重验 manifest/digest；它信任上游已审核的登记与 evaluator。
- 当前 helper 返回结算结果，但不会自动持久化回写登记文件，未完成调度/对账/崩溃恢复。
- 已配置但未结算的项目再次走同一 helper，会先重复 configure 而失败；生产级补偿需显式读链状态后继续 settle 或 renew。
- beneficiary 与外部贡献者真实身份/钱包控制没有完整绑定机制。
- **连接的是旧 Arena 的局部本地研究，不是当前 PayAssist，也不是 XEXP 演示或 Flower。**

### 4.5 BountyRound：准确叫作“承诺与裁决领奖原型”

[BountyRound.sol](../../contracts/src/BountyRound.sol) 和 [对应测试](../../contracts/test/bounty-round.test.js) 实际提供：

1. owner 通过 `commitRound` 固定目标版本哈希、任务规格哈希、截止时间。
2. 任意调用地址通过 `submitClaim` 提交 material hash；同一轮次/同一 hash 的首个提交地址优先，每轮最多 10,000 个承诺。
3. owner 用 `fundRound` 预充**本地链原生币**池，不是 XEXP，也不是 RTM。
4. 截止后仅 owner 可 `finalizeRound` 提供 valid flags 和金额，批准总量不得超过已充池。
5. 被批准的原提交者以 `claimPayout` 拉取款项，禁止他人领取或重复领取；付款前先置 paid，转账失败则回滚。

**源码没有 `reveal` 方法，也没有链上提交材料原像、盐值或揭示一致性校验。** 历史文档、注释和测试标题中的 commit–reveal 是设计称谓，不是完整揭示机制已实现的证据。测试中的 `verifier` 变量并非独立链上验证角色；裁决权限实际是 `onlyOwner`。

同 hash 优先只提供该 hash 的登记顺序，不证明贡献真实、语义唯一、不被抢先复制或没有女巫提交。现有正/负例测试也不是对裁决数组重复项、异常收款合约、全部资金记账和公网攻击面的完整审计。

旧 HTTP 会话的配额/TTL/有限反馈原型与 BountyRound 分别存在，但身份认证、材料复现、揭示验证和最终判奖未贯通，不能宣称已经开放“公众安全投稿—独立复现—自动真实领奖”。

## 五、Flower：贡献认可为何独立于金融奖励

### 5.1 资产性质与角色

[ContributionFlower.sol](../../contracts/src/ContributionFlower.sol) 的名称/符号是 `REDTEAM Flower / FLOWER`，继承 ERC-721，支持 ERC-5192 的锁定接口与事件。这是独立 NFT 合约，不是 RTM 名称迁移，也不以 RTM/XEXP 为持有权益。

- **owner** 通过 `setIssuer` 管理发行者，另有继承的管理权转移/放弃接口；这些操作不改变任何 NFT 持有人，也不直接赋予 mint/revoke 权限。owner 仍可通过轮换发行者改变实际发行控制，不能把角色区分说成强制多方治理。
- **issuer** 调用 `mint` 与 `revoke`；接收者有签名也不能自行发放。
- **recipient** 必须是签名对应的普通 EOA；当前拒绝有代码的地址，不支持 ERC-1271 合约钱包、代理接收或管理员换钱包。

代码区分 owner 与 issuer 的角色，演示使用不同测试账户；构造函数没有强制二者地址必须不同。若将来治理设计要求分人、多签或组织分权，必须另作明确实施与验收，不能仅凭存在两个字段就宣称完成。

### 5.2 接收者究竟签了什么

EIP-712 domain 是 `REDTEAM Flower / 1`，绑定实际 chain ID 与 verifying contract。`Consent` 的六个字段为：

```text
recipient, contributionId, category, nonce, deadline, policyVersion
```

`mint(Consent consent, bytes signature)` 只允许 issuer 调用，检查非零地址/贡献 ID、EOA、类别 0/1/2、固定政策版本、每个接收者的 nonce、期限和签名恢复地址。成功时消耗 nonce 与贡献 ID，写入类别/发行时间，mint 并发出 Locked/FlowerMinted；错误则回滚。

边界有一个应明确的小差异：合约允许 `block.timestamp == deadline`，链下 helper 为留余量要求 `deadline > now`。两者对应测试已分别表达，不能把任意一侧的边界描述成另一侧。

**签名证明接收者密钥对上述条款的同意，不证明真实姓名、审核者身份、贡献真伪、漏洞价值或法律许可。** Consent 不包含 evidence SHA-256；不能说接收者“签署了证据摘要”，也不能说合约“验明了审核材料”。

### 5.3 链下审核、摘要与稳定贡献标识

[flower-protocol.js](../../contracts/scripts/flower-protocol.js) 的 `validateReviewedRecord` 检查严格 schema、可信预期上下文、合成材料、审核声明、原始文件 SHA-256 与 EIP-712 同意。材料只允许可信绝对根目录下的相对普通文件，拒绝路径穿越、符号链接/连接、过大文件与远程 URL；输入契约拒绝额外金额、payout 等金融字段。

类别含义是：

| category | 要求表达的贡献 | 不应误称 |
|---|---|---|
| model / 0 | 攻击臂模型违规、系统未违规；干净对照不违规且两臂有效触达 | 基础模型训练改善或系统已实际突破 |
| system / 1 | 攻击臂有系统违规；干净对照不违规且两臂无基础设施错误 | 仅模型提出请求就发生了真实资金损失 |
| research / 2 | 研究贡献，confirmation 为 null | 已完成配对攻击突破 |

这些字段在当前样例中是**受信任本地控制者的 JSON 声明**。`reviewerReference`、`auditReference`、`audited: true` 不是审核人密码学签名、生产身份认证或事实 oracle。格式、摘要与配对字段自洽，只说明材料符合本地输入契约；恶意审核者仍可能声明假事实。

Flower 的贡献 ID 由固定字段顺序的 `{protocol: 'redteam-flower', version: 1, contributionKey}` 经 keccak256 推导，排除受益钱包、类别、文件名、nonce 和全部金融金额。证据 SHA-256 仅在可信链下绑定审核材料；合约不读取文件、不校验证据摘要。**Flower 稳定贡献 ID 与 RTM 的含金额 claim ID 是两个协议，不能混用。**

### 5.4 不可转让、去重与不可逆撤销

- `transferFrom`、两个 `safeTransferFrom` 调用路径、自转、零地址目标均禁止；`approve`、`setApprovalForAll` 也直接拒绝。
- 底层 `_update` 只允许给尚无 owner 的 token 非零地址 mint；不允许转移、重新 mint 已有 token 或 burn，且这个 override 不可再覆写弱化。
- `locked(tokenId)` 对存在的 token 永远为 true；撤销不会解锁。
- `contributionUsed` 在**同一合约实例内**跨接收者、跨类别去重，撤销也不释放 ID。更换 contributionKey 可得到新 ID，语义重复仍需人工判断；不同部署间也没有自动共享去重。
- `revoke` 仅把 `revoked` 永久设为 true，保留原 token、owner、贡献关联、nonce 与发行历史。没有 `unrevoke`、burn、重分配或钱包迁移接口。

因此“管理员可撤销认可”不等于“管理员可收回 NFT 并换人发”；遗失钱包、异议申诉、撤销理由、发行者密钥安全和继任治理仍需独立处理。

### 5.5 元数据和演示的真实含义

`tokenURI` 是内嵌 base64 JSON，图片是固定 base64 SVG，不调用外部图床，也不接受任意用户艺术输入。包含 Token number、Category、Status：**小花图案固定，认可状态随撤销变动**，不是所有元数据都永久固定。

展示元数据省略钱包和贡献摘要，但 `ownerOf`、贡献映射及 mint/Transfer 事件仍公开地址和贡献 ID。hash 不等于匿名，撤销也不是数据删除。当前演示只使用合成材料与测试钱包。

[flower-demo.js](../../contracts/scripts/flower-demo.js) 在拿 signer 和发交易之前运行 `assertLocalNetwork`，要求进程内 Hardhat、chainId 31337、无远程 URL、无配置/运行时分叉，并交叉检查 provider/RPC chain ID 和 Hardhat metadata。再次检查后才 mint。

这个限制属于官方 helper/演示路径；Solidity 合约本身没有把 chainId 写死为 31337，不能宣称“合约从技术上绝不可能被他人部署到公链”。本次没有部署到公网链的授权或操作。

演示用真实本地合约回滚验证拒绝转让/授权，再撤销**同一枚 token**，导出 [flower-demo.json](../site/flower-demo.json)。两份快照是一个 token 的两个时间点，不是两枚资产，不是实时查询，也不代表临时本地链仍在持续运行。导出不含签名、原始证据、审核引用、测试钱包或私钥。

## 七、信任模型与至少八项上线缺口

**核心信任关系是：合约检查机械规则，可信宿主/审核者判断业务与贡献，钱包签名确认具体条款。任何一层都不能被另一层的“通过”替代。**

| 缺口/残余风险 | 当前实际边界 | 下一步必须形成的验收证据 |
|---|---|---|
| 1. 真实身份与公开投稿 | 钱包控制≠真实身份；审核引用只是声明；HTTP 与链上未贯通 | 明确授权主体、账户/角色、钱包证明、认证/限流与冒用拒绝测试 |
| 2. 贡献事实与语义去重 | digest 只校验字节，ID 去重只针对相同标识 | 审核流程、原始材料复核、换键重复与误判/申诉样例，不能只增加 hash |
| 3. Flower 发行治理 | owner 可轮换 issuer，issuer 可发行/永久撤销 | 角色分权、密钥保护、轮换/继任、撤销理由与申诉流程；验证不是依赖单人声明 |
| 4. 不可转让钱包残余风险 | NFT 不能转，不代表私钥/钱包不能出售、泄漏或受胁迫 | 风险披露与账户治理评估；不得许诺技术上杜绝全部交易或控制权转移 |
| 5. 公链隐私与不可删除历史 | 元数据去敏不消除 owner/events；撤销不擦除 | 数据最小化、公开同意、关联风险、保留/披露评估；仅用合成数据做初期演练 |
| 6. 公网部署与网络兼容 | 官方 Flower 演示仅本地，编译目标 Cancun；没有发行上线证据 | 明确目标链、兼容测试、字节码/配置审查、授权与独立审计，再决定是否允许部署 |
| 7. RTM 奖励资金与权限 | 金额依赖 evaluator；累计上限须配置，续期受预算约束 | 实际限额/暂停/轮换及恶意评估者测试、预算不足处置；不宣称保证兑付 |
| 8. 桥接持久化与重试 | helper 信任登记并返回结果，未做生产对账/恢复 | 重算绑定、完整证据验证、读链终态、配置后失败补偿、崩溃恢复与不可重复奖励 |
| 9. BountyRound 完整提交协议 | 有 commit 与 owner 裁决，无 reveal 校验或完整公众身份绑定 | 原像/盐/受益人绑定设计、抢先复制与重复裁决等对抗测试、端到端复现判奖 |
| 10. 当前主线安全边界 | Flower 不修复 PayAssist，也不证明基础模型改善 | 依原研究协议处理开放发现与回归，不用荣誉 NFT 遮盖未解决问题 |
| 11. 法律与商业资格 | 免费/NFT/不可转让均不构成合法性保证 | 独立国内合规化报告与专业法律/隐私审查；口头建议不是正式批准 |

本报告不推导 NFT 能解决账号销售、支付许可、真实身份或法律适用问题。未建立客户、生产资金或生产发行体系，也不对外提供“安全认证”保证。

### 优先级 P0：维持清晰边界和可复核性

1. **将日期化结果与当前基线对齐。** 保留首轮记录，补充本轮命令/范围/通过失败、运行环境与源提交；不要覆写历史分支状态。

### 优先级 P2：任何真实发行前的停止线

只有法律/隐私审查、角色治理、密钥方案、申诉撤销、目标网络兼容、独立安全审计和受控试点均有明确书面结果，才讨论是否真实发行。即使上述工作完成，也不自动导出“合法”“绝对安全”或“有金融收益”的结论。

**未满足这些条件，继续停留在本地合成原型：不公开发行、不接真实资金、不自动给当前 PayAssist 结果发奖或铸 NFT。**
